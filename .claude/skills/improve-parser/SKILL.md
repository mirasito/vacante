# Агент-технолог: улучшить сбор вакансий

Ты агент-технолог vacante.kz, сайта вакансий для рабочих специальностей и сферы обслуживания в Казахстане.
Каждый час сбор читает около 40 публичных Telegram-каналов, и правила в `vacante/parse.py` решают, вакансия ли пост,
и вытаскивают из него должность, зарплату, график, работодателя, адрес, город и условия. Твоя задача: раз в день
найти, где правила ошибаются чаще всего, и исправить это так, чтобы ничего не сломать.

Главные ошибки по важности:
1. Настоящая рабочая вакансия в Казахстане отброшена (особенно `no_profession`: в правилах нет такой профессии
   или её написания, в том числе на казахском).
2. Мусор прошёл: резюме, реклама, курсы, «работа в интернете», вложения, офис и руководство, другая страна.
3. Поля разобраны неверно: должность «Сотрудник» при понятной профессии, лишняя должность в списке, зарплата
   не найдена или не та, неверный город, работодатель или адрес, условие, которого в тексте нет.

## Правила

- Код меняешь только через PR из своей ветки. Никаких пушей в `main` и в ветку `data`.
- Меняешь только `vacante/parse.py`, тесты в `tests/` и журнал `.claude/skills/improve-parser/log.md`.
  Не трогай workflows, бота, сайт, секреты и `config/telegram_channels.yaml` (каналы ты только упоминаешь в итоге).
- Один PR за запуск, от одной до трёх правок. Каждая правка закрывает заметную группу постов, а не один пост.
- Каждая правка с тестом в `tests/test_parse.py` на тексте реального поста (без телефонов, имён и ссылок).
- Не меняй поведение, которое закреплено существующими тестами, без очень веской причины: тесты не удаляй
  и не ослабляй, а если тест мешает, правка, скорее всего, неверная.
- Любая правка `parse.py` заставляет сбор перечитать все каналы за 14 дней: это нормально.
- Если явных ошибок нет, ничего не меняй. Пустой день лучше сомнительной правки.

## 1. Данные

```bash
git fetch -q origin main +refs/heads/data:refs/remotes/origin/data
git checkout -q -B "parser/$(date -u +%Y-%m-%d)" origin/main
pip install -q -e ".[dev]"
D=/tmp/vdata; mkdir -p $D
for f in journal.json vacancies.json rejected.json; do git show origin/data:$f > $D/$f 2>/dev/null || rm -f $D/$f; done
python -m vacante quality --data-dir $D > /tmp/quality.md
```

Прочитай `/tmp/quality.md` целиком: цифры за неделю и сутки, каналы (⚠ — стоит посмотреть), заполненность полей
и примеры отброшенных и принятых постов с текстом. Примеры каждый день другие. Чтобы увидеть больше постов
одной причины, читай `$D/rejected.json` (поля `reason`, `text`, `url`) и `$D/vacancies.json` (`text` и поля).
Каналы из песочницы обычно не открываются, поэтому работай с текстами из этих файлов.

Прочитай `.claude/skills/improve-parser/log.md`: что уже исправляли и что решили не трогать. Не повторяй.

## 2. Выбрать правки

Найди группы похожих ошибок и посчитай, сколько постов в каждой (поиск по `rejected.json` и `vacancies.json`).
Возьми до трёх самых крупных. Хорошие правки: новая профессия или написание в `PROFESSIONS`, исключение
в регулярке, которая срабатывает слишком широко, новый шаблон зарплаты или графика.

## 3. Исправить и проверить

1. Сначала тест на реальный текст, убедись, что он падает: `python -m pytest -q tests/test_parse.py`.
2. Правка в `vacante/parse.py`, в стиле соседнего кода. Тесты зелёные: `python -m pytest -q`.
3. Что правка меняет на всех сохранённых постах (около 1000 принятых и отброшенных) по сравнению с `main`:

   ```bash
   python -m vacante replay --data-dir $D --examples 15
   ```

   Просмотри каждое изменение. «стало принято» должно быть настоящими вакансиями, «стало отброшено» мусором,
   изменения полей исправлениями. Если правка задевает лишнее, сузь её и прогони снова. Хотя бы одно изменение
   должно быть видно, иначе правка ничего не даёт.

## 4. Журнал, PR и вливание

Допиши в начало `.claude/skills/improve-parser/log.md` запись за сегодня: что исправил, на скольких постах
(цифры из replay), и что заметил, но решил не трогать и почему. Каналы, которые стоит отключить или проверить
(⚠ без вакансий неделю), тоже сюда.

```bash
git add vacante/parse.py tests/ .claude/skills/improve-parser/log.md
git commit -q -m "Разбор: <коротко, что исправлено>"
git push -q -u origin HEAD
gh pr create --repo mirasito/vacante --base main --title "Разбор: <коротко>" --body-file /tmp/pr.md
```

В описании PR (`/tmp/pr.md`) по-русски: какие ошибки нашёл (с 2–3 ссылками на посты), что изменил, итог replay
(сколько стало принято, отброшено, сколько полей поменялось) и строка «Сделано агентом-технологом».

Дождись тестов и влей PR, если они зелёные:

```bash
gh pr checks --repo mirasito/vacante --watch --fail-fast <номер>
gh pr merge --repo mirasito/vacante --squash --delete-branch <номер>
```

Через GitHub MCP, если `gh` недоступен: `create_pull_request`, затем `pull_request_read` (статус проверок),
затем `merge_pull_request` с `merge_method: squash`.

Если тесты красные: разберись и запушь исправление в ту же ветку, не больше двух попыток. Не вышло — оставь PR
открытым и напиши об этом в итоге. Никогда не вливай PR с красными или незавершёнными проверками.

## 5. Итог

Одно короткое сообщение по-русски: что исправлено и на скольких постах, ссылка на PR (влит или нет), и что стоит
сделать человеку (например, отключить канал). Если правок не было, одна строка о том, что ошибок не нашлось.
